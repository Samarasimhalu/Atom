Native mobile automation

Generate and run iOS and Android automation through a managed execution boundary.

ATOM supports a mobile generation type that requires a declared platform. It emits managed WebdriverIO TypeScript with stable accessibility-id locators; native execution uses a separate immutable Appium worker and the approved platform device broker.

iOS XCUITest HTTPS iOS device broker on the Appium-private network · Uses @wdio/globals and accessibility-id locators such as ~primary-action.
Android UiAutomator2 HTTPS Android device broker on the Appium-private network · Uses @wdio/globals and accessibility-id locators such as ~primary-action.

New · Atom Pulse

Test what your customers actually do, not just what you remembered to test.

Atom Pulse turns anonymized real-user journeys into a ranked list of untested paths. It reports a real-user coverage percentage, then drafts a regression test for each gap through the same governed pipeline: policy checks, human approval, and audit trail.

1 · Capture Privacy-first SDK One script tag records navigation, clicks, submits, JS errors and failed requests. It never records typed values and honors Do Not Track.
2 · Mine Journeys, ranked by risk Sessions are scrubbed, grouped into journeys, and scored by traffic, error rate and revenue paths such as checkout.
3 · Close the gap Governed test generation One click sends a gap to the AI gateway. The drafted test still goes through approval before anything runs.
4 · Ask “Hey Atom” voice copilot Ask “What’s my coverage?” or “Generate a test for the top gap”. Uses the browser’s built-in speech, with no extra service.

API testing and orchestration

Chain API tests with controlled data flow, not ad-hoc scripts.

ATOM accepts a versioned api-test-plan/v1 contract. Each plan is declarative: it defines bounded requests, assertions, safe response extraction, and later placeholder resolution without allowing arbitrary code execution.

Execution model
  1. 01ValidateSchema, path, method, and JSON-path checks
  2. 02AuthorizeTenant, policy, approval, and egress gates
  3. 03ChainExtract a value and resolve only later references
  4. 04ReconcilePersist evidence and safely update operators
api-test-plan/v1 Declarative Forward-Only Chaining Example 
{
  "environment": "staging",
  "steps": [
    {
      "id": "create-order",
      "request": { "method": "POST", "path": "/v1/orders" },
      "assertions": [{ "type": "status", "equals": 201 }],
      "extract": [{ "name": "orderId", "path": "$.id", "classification": "internal" }]
    },
    {
      "id": "get-order",
      "request": { "method": "GET", "path": "/v1/orders/{{chain.orderId}}" },
      "assertions": [{ "type": "json_path_equals", "path": "$.state", "equals": "created" }]
    }
  ]
}
⊕

Forward-only chaining. A step can capture a named value from a response and reference it in a later request with {{chain.variable}}. Duplicate variables, unresolved placeholders, unsafe JSON paths, and forward references are rejected before execution.

Contract

Constrain the request surface.

Plans require a name, environment, bounded unique steps, allowlisted HTTP methods, relative paths, JSON-only bodies, and normalized headers. The test specification validates the API plan before it becomes executable.

Assertions

Make response expectations explicit.

Use status checks, JSON-path existence or equality checks, and header equality checks. A failed assertion ends the dependent chain so later requests cannot run against an invalid state.

Extraction

Pass values safely between steps.

Extraction rules accept safe body JSON paths and record only presence and classification in step results. Secret-classified values are not surfaced in live or result payloads.

Orchestration

Keep run state durable and observable.

Authorized submission, idempotency, policy gates, isolated execution, and replayable lifecycle events preserve an accountable path from request through evidence.

Governance in the execution path

Automation should be fast, not unaccountable.

ATOM keeps the test lifecycle explicit from request to retained evidence. It supports a least-privilege identity model and fails closed when the prerequisites for safe execution are absent.

01

Identity and tenant context

OIDC-ready authentication, role-based permissions (viewer, developer, approver, admin, owner), and tenant-scoped access to runs, approvals, audit events, and artifacts.

ENFORCED
02

Policy and approvals

Execution decisions bind the specification, intent, idempotency key, session, and policy version to prevent replay or substitution.

BOUND
03

Isolated execution

Runs dispatch to a hardened Playwright or Appium worker image with constrained results, artifact quotas, and a fail-closed egress posture.

ISOLATED
04

Evidence and retention

Authorization-aware artifact access, durable run states, replayable events (AtomRunStream), audit records, and configurable retention tombstones.

TRACEABLE
Architecture and durable operations

Control plane separated from isolated execution workers.

PostgreSQL is the source of truth for runs, state transitions, event history, audit records, artifact metadata, and quota usage. Redis/BullMQ coordinates durable job dispatch, and S3-compatible storage holds private tenant-scoped artifacts.

  • Identity + RBAC Boundary Development headers, HS256 JWTs & OIDC/SAML role mapping
  • Allowlisted AI Gateway Input redaction, token budgets, AI evaluation harness & audit events
  • Policy & Approval Engine Single-use approvals, domain denylists & timeout guardrails
  • PostgreSQL & Redis/BullMQ Run state machine, idempotency keys & sequence-numbered events
  • Authorization-Aware S3 Artifacts Private object storage, short-lived signed URLs & retention cleanup
  • Immutable Playwright & Appium Workers Digest-pinned, non-root containers with Trivy CVE gating
